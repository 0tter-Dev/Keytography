# Interface Web

## Purpose

Interface web do Keytography — a primeira interface de usuário do projeto, consumindo o core/backend já implementado (autenticação, cofre, avaliação e geração de senha). Serve deliberadamente como instância de teste/iteração: é aqui que identidade visual, responsividade, convenções de código de interface, animações, interações e experiência do usuário são definidas e evoluídas antes de qualquer portabilidade para mobile ou desktop (ver [PROJECT-ARCHITECTURE.md](../../PROJECT-ARCHITECTURE.md#architectural-direction)).

## Current Status

`in_progress` — fundação entregue em `keytography-007` (projeto `web/`, tooling, sistema de temas, i18n, cliente de API tipado, casca de layout responsiva, CI) e telas de autenticação entregues em `keytography-008` (registro, verificação de e-mail, login, esqueci/redefinir senha, rotas protegidas), com a sessão gerenciada pelo backend adotada em `keytography-017` (access token em memória, restauração por refresh, renovação silenciosa, logout real e detecção de troca de conta entre abas). A tela inicial ainda é a de estado do sistema. As telas de cofre, avaliação, geração, configurações e supervisão do Admin vêm nos planos `009` a `013`, e o polimento final em `014`.

## Key Rules

- **Stack**: React + TypeScript + Vite (ver [PROJECT-ARCHITECTURE.md](../../PROJECT-ARCHITECTURE.md#selected-technology-direction) para a decisão e a alternativa descartada). Projeto em `web/` na raiz do repositório, toolchain Node/npm separado do backend .NET.
- **Convenções de código**: [web-frontend-conventions.md](../../guides/web-frontend-conventions.md) define componentização reutilizável, variantes tipadas (`cva`), tokens de design, proibição de CSS inline/ajustes pontuais, nomenclatura, i18n e testes — vale como padrão geral do projeto para toda interface futura, não só para esta capability. Bibliotecas só entram no plano que as usa (ver tabela no guia).
- **Dados da API**: todo acesso passa por um cliente tipado (`openapi-fetch`) gerado do contrato [`docs/reference/openapi.json`](../../reference/openapi.json), que a própria API produz; teste do backend e CI do frontend impedem que o contrato e os tipos fiquem desatualizados. **Manter esse contrato é obrigação de quem muda a API** (regenerar `openapi.json` e `schema.d.ts` na mesma entrega; ver [ADR-0004](../../decisions/ADR-0004-versioned-openapi-contract.md)). A API libera CORS só para as origens configuradas (`Cors:AllowedOrigins`; padrão: servidor de desenvolvimento do Vite em `localhost:5173`).
- **Sistema de temas**: 5 temas (`system` — padrão inicial, segue `prefers-color-scheme` — `light`, `light-high-contrast`, `dark`, `dark-high-contrast`) × 9 cores de destaque (verde, verde-limão, roxo, vermelho, azul, azul-claro, laranja, amarelo, rosa), via CSS custom properties. A cor de texto sobre elementos de destaque é calculada pela luminosidade da cor escolhida, não fixa, para garantir contraste nos modos de alto contraste. Persistido em `localStorage` (sem backend) — sincronização entre dispositivos fica para quando sincronização em nuvem deixar de ser um Non-Goal. A infraestrutura (tokens, store, aplicação no `<html>`, anti-flash) existe desde `keytography-007`; um seletor temporário só aparece em desenvolvimento, e a UI definitiva de seleção chega em `keytography-012`. O destaque tem três papéis: preenchimento (`primary` + texto calculado pela luminosidade, ≥ 5.14:1, WCAG AA = 4.5:1), traço sobre o fundo — foco e ícones — (`accent-ink`: o mesmo destaque com a luminosidade limitada por tema, ≥ 3.4:1 contra fundo e superfície nas 36 combinações tema × destaque, WCAG 1.4.11 = 3:1) e nenhum outro uso (texto corrido não usa o destaque). Uma guarda automática (`contrast.test.ts`) lê os tokens reais e falha se isso regredir; detalhes e regras de uso em [web-frontend-conventions.md](../../guides/web-frontend-conventions.md#temas-e-cores-de-destaque).
- **i18n**: sistema 100% `pt-BR` por agora, mas já estruturado via `react-i18next` desde `keytography-007` (um único arquivo de tradução) para que adicionar idiomas depois seja só tradução, não reescrita. `en` e `es` são planejados para depois da consolidação da interface web, antes de Mobile/Desktop começarem (ver [PROJECT-ARCHITECTURE.md](../../PROJECT-ARCHITECTURE.md#architectural-direction)).
- **Preferências de exibição**: densidade de listagem (Tabela/Lista/Cards/Blocos) e avatar gerado (iniciais do Login + cor de fundo escolhida entre as 9 cores de destaque) serão preferências locais (`localStorage`), a implementar em `keytography-012` (planejado, ainda não existe).
- **Casca de layout**: sidebar recolhível no desktop (`md+`) e barra superior com menu hambúrguer + drawer no mobile; itens de navegação sem tela ainda aparecem como placeholders desabilitados. No rodapé da navegação (sidebar e drawer) ficam o login do usuário logado (`GET /auth/me`) e o botão "Sair".
- **Autenticação** (`features/auth/`, `keytography-008`): telas em `pt-BR` para registro (`/register`, com confirmação de senha), verificação de e-mail (`/verify-email`, campo de token), login (`/login`), "esqueci minha senha" (`/forgot-password`) e redefinição (`/reset-password`, token + nova senha). Formulários com React Hook Form + Zod, com as mesmas regras da API (senha ≥ 8 caracteres; e-mail com `@`); as mensagens vêm do arquivo de tradução. Os erros são explicados por tipo, não pelo texto do servidor: credenciais inválidas dão uma mensagem única que não revela se errou o login ou a senha; e-mail não verificado (403) tem mensagem própria e um atalho para a verificação; "esqueci a senha" responde igual exista ou não o e-mail. Em desenvolvimento a API não envia e-mail (registra o token no log), e o usuário o cola nas telas.
- **Sessão e rotas protegidas** (decisão no [ADR-0006](../../decisions/ADR-0006-backend-managed-sessions.md); o modelo de cliente anterior, `sessionStorage` e logout local, está no [ADR-0005](../../decisions/ADR-0005-client-session-model-and-backend-managed-sessions.md), substituído): a sessão é gerenciada pela API. O cliente guarda só o **access token** (JWT de 15 minutos por padrão) **em memória** — nada em `localStorage`/`sessionStorage` —, e o refresh token vive em cookie `HttpOnly`, que o script nunca lê. Ao abrir a aplicação (F5, nova aba), o `SessionController` tenta `POST /auth/refresh` (`credentials: 'include'`); as rotas protegidas e as de visitante mostram um estado de carregamento até a resposta, sem piscar o login. Se a API não responde (o refresh tem tempo limite de 20 s), a tela é liberada no login e um aviso informa que não foi possível falar com o servidor. Com sucesso, a pessoa entra direto; sem cookie válido, vai ao login (sem aviso de expiração: nunca houve sessão nesta aba). O access token é **renovado pouco antes de vencer** (30 s) e, ao receber 401 em uma chamada autenticada, o cliente tipado renova a sessão e **repete a chamada uma única vez**; chamadas simultâneas compartilham **um único** refresh, e o intervalo entre renovações agendadas nunca é menor que 5 s (sem laço de refresh se o token já nasce dentro da janela). Se o refresh é rejeitado (401), a sessão termina como expirada e o login avisa; se a API não responde, a sessão não é derrubada (nova tentativa em 15 s; se o token vence sem renovação, termina — e um refresh ainda em andamento no vencimento é esperado antes disso). Logout ou expiração durante um refresh em voo descarta a resposta dele (uma resposta tardia não reabre a sessão encerrada). Um 401 que persiste depois de um refresh bem-sucedido (por exemplo, cofre sem DEK em cache após reinício do servidor) avisa a API (`logout`, em segundo plano, para o cookie não restaurar uma sessão sem DEK) e leva ao login como expirada, sem laço. **Logout real:** "Sair" chama `POST /auth/logout` e só então limpa o estado local e o cache; se a API não responde, limpa mesmo assim e avisa que a sessão no servidor pode continuar até expirar. **Troca de conta entre abas:** o cookie de refresh é compartilhado pelo navegador e um novo login substitui a sessão do cookie anterior; depois de cada renovação o cliente compara o usuário (`GET /auth/me`, com nova tentativa a cada 15 s se a leitura falhar) com o que a aba mostrava e, se for outra conta, descarta o cache, avisa ("Você entrou com outra conta em outra aba ou janela…") e volta ao início já como a conta atual; sendo a mesma conta, nada muda. O cache de consultas é esvaziado quando a sessão termina ou a conta muda (não a cada renovação). Toda rota fora de autenticação passa por `RequireAuth`, que redireciona ao login guardando o destino (restaurado ao entrar; só caminhos internos são aceitos); login, registro e "esqueci a senha" redirecionam quem já está logado ao início; `/verify-email` e `/reset-password` funcionam com ou sem sessão. O cliente tipado nunca anexa o JWT aos endpoints anônimos nem ao refresh.
- **Supervisão do Admin**: a interface planejada para esta fase (`keytography-013`, ainda não implementada) cobrirá só o que o backend já expõe — leitura de cofre de outro usuário e recálculo retroativo de avaliação. Um painel mais completo é evolução futura (ver abaixo).

- depends on [authentication-and-users](../authentication-and-users/README.md): consome `POST /auth/register`, `/verify-email`, `/login`, `/forgot-password`, `/reset-password` e `GET /auth/me`; toda tela além dessas exige um usuário autenticado; também consumirá o endpoint de troca de senha autenticada (`keytography-012`).
- depends on [vault-entries](../vault-entries/README.md): consome os endpoints de CRUD de cofre.
- depends on [password-evaluation](../password-evaluation/README.md): exibe a nota de força e o detalhamento por critério já retornados pela API.
- depends on [password-generation](../password-generation/README.md): consome o endpoint de geração de senha.

## Future Considerations

Ideias discutidas e deliberadamente fora do escopo desta fase — registradas para não se perderem, não para implementação imediata:

- **Configurações de conta completas**: nome de exibição editável e upload de imagem de perfil real (hoje: avatar gerado por iniciais + cor, sem upload). Exige mudança de schema/armazenamento no backend.
- **Painel de Admin completo**: diretório/listagem de todos os usuários do sistema, e métricas/saúde agregada (além da supervisão de cofre já implementada). Exige endpoints novos no backend.
- **Cor de destaque customizada**: seletor de cor livre, além das 9 cores curadas atuais.
- **Organização de entradas de cofre**: tags, favoritos, e um esquema de grupos/subgrupos. Exige mudança de schema em `vault-entries`, fora do escopo de uma capability só de interface.
- **i18n além de `pt-BR`**: inglês e espanhol, planejados para depois da consolidação desta interface, antes de Mobile/Desktop.
